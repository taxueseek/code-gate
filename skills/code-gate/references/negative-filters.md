# 证据链自检：八不报、反例自检与四问抗辩（Negative Filters & Gotchas）

代码审查的信誉建立在**零噪音（Zero Noise）**之上。一条无病呻吟的误报会训练开发者忽略真正致命的缺陷。所有档位都走同一条证据链漏斗，档位只决定「过几遍、谁过」，不决定「过哪几套规则」：

```
候选发现
  -> [过滤] 八不报铁律（第一节）：命中即静默丢弃
  -> [铁证] 三件套：CRITICAL / HIGH 缺任一要素则降级或丢弃
  -> [自检] 出口前反例自检表（第三节）：逐条对照，翻车形状即修正或丢弃
  -> [抗辩] verification_pass: true 时走四问抗辩（第四节），标 CONFIRMED / PLAUSIBLE；
            false 时直出且严禁标记
  -> 存活发现
```

---

## 一、 八不报铁律（Strict Negative Filters）

任何候选发现一旦命中以下任一条款，立即静默丢弃。**唯一例外**：第 1 条在本地报告模式下允许「极高危存量隐患」以文末独立一行 `pre-existing notes:` 呈现（格式见 `action-modes.md`），绝不混入正式发现列表；PR 评论模式下该例外同样禁用，一律绝对剔除。

### 1. 非本次变更引入的存量旧账（Pre-existing Issues）
- **判定**：该缺陷在 base commit 中已原样存在，且本次变更未触及、未恶化、亦未改变其调用可达性。
- **处置**：见本节开头的唯一例外。远端 PR 评论模式绝对剔除。

### 2. 单行看似有病但全链路已被保护的假警报（Protected in Context）
- **判定**：孤立看某行似乎缺少空值检查或越界保护，但上游路由、校验器、状态机不变量或框架底层已确保该非法状态不可达。
- **处置**：未核实上游调用方与下游消费方前，不得仅凭单行代码或函数名臆测报出。

### 3. 资深工程师不会在 PR 中挑刺的细枝末节（Cosmetic Nitpicks）
- **判定**：纯属个人风格偏好且不影响正确性、可读性与可维护性的微调（如无二次赋值的 `let` 改 `const`、两行局部逻辑内联或拆分、局部短变量重命名）。
- **处置**：立即丢弃。除非属于「顺手改」且在同一文件的结构简化建议中附带一笔，否则绝不单独成条。

### 4. 编译器、Type Checker 或既有 Linter 必拦的机械错误（Tool-Catchable Issues）
- **判定**：项目已配置的 `tsc`、`mypy`、`cargo check`、`eslint`、`ruff` 等工具 100% 会报错的缩进、分号、明显类型不匹配或缺失导入。
- **处置**：不替编译器和格式化器打工（若在本轮运行了验证命令且报错，在 `verification` 台账中如实报告命令输出即可）。

### 5. 无规约原文支撑的宽泛说教（Vague Quality Advice）
- **判定**：「建议补充更多单元测试」「建议增加注释和文档」「建议未来拆分为微服务」等无法指向具体代码改法的空泛建议。
- **处置**：凡指控违反项目规范，必须逐字引用生效的 `CLAUDE.md`、`AGENTS.md` 或 `.opencodereview/rule.json` 原文；拿不出原文引用的泛泛说教一律丢弃。

### 6. 代码中已显式标注豁免的规则（Explicitly Suppressed）
- **判定**：代码已包含 `// @ts-ignore`、`// @ts-expect-error`、`/* eslint-disable */`、`# noqa`、`#[allow(...)]` 或 `// SAFETY:` 注释说明原因。
- **处置**：尊重作者显式声明的工程权衡，除非能证明该豁免直接引发运行时崩溃或高危安全漏洞。

### 7. 与作者声明意图一致的刻意改造（Intentional Behavior Change）
- **判定**：PR 描述、Commit Message 或关联 Issue 已声明本次旨在「废弃旧接口、调整默认行为或迁移协议」，而审查却报警「破坏了旧行为」。
- **处置**：将深思熟虑的需求演进当成回归缺陷属于未读上下文的低级失误，立即剔除。

### 8. 未被 Diff 触及且无调用交集的无关区域（Unrelated Unmodified Code）
- **判定**：同一文件或相邻文件中与本次改动无控制流、数据流、契约交集的未修改代码段。
- **处置**：严禁顺着打开的文件漫游发散。

## 二、 三件套铁证与四问抗辩

### 1. 三件套铁证（全档位适用）
每条 `CRITICAL` 与 `HIGH` 发现必须同时具备：（1）精确 `file#Lstart-Lend`；（2）触发错误的具体输入或状态序列；（3）为何现有防线（上游校验、类型系统、框架默认处理）拦不住。缺一则降级为 `MEDIUM` / `LOW` 或丢弃。

### 2. 四问抗辩（仅 `verification_pass: true` 适用）
复核环节站在代码作者立场，逐条尝试推翻候选发现，四问与三态裁决标准见 `scoring-rubric.md` 第二、三节。存活项标 `CONFIRMED` 或 `PLAUSIBLE`，`REFUTED` 静默丢弃。派发方式由 `review_plan.verification_mode` 决定（`centralized` / `per-finding`）。

## 三、 出口前反例自检表（Pre-Output Gotchas —— 源自 `review-suite` 与 `check`）

在生成最终报告或执行 `--fix`、`--comment` 前，逐条对照以下高频翻车反例自检：

| 反例形状（What Happened） | 强制处置规则（Rule） |
|---|---|
| 凭函数名或变量名想象出一条 `HIGH`，重读代码后发现根本不成立 | 每条发现必须写清「具体什么输入或状态 → 走哪条分支 → 产出什么错误结果」，写不出具体触发链路即删 |
| 大 Diff 被命令行分页器或 `head` / `tail` 截断，却声称「已审完所有文件」 | 只跑 `review_plan.diff_command`（已带 `--no-pager`）；按 `inventory_file` 的完整账本分批读，用 `total_files` 对账实际已读文件数，未读完必须如实标注 |
| PR 取数失败却对空文件账本继续出报告 | `precheck_verdict` 为 `ERROR` 时直接结束，且 `--force` 不得覆盖；仅 `SKIP` 可被覆盖 |
| 修了一处缺陷，同仓库里一模一样的另外 N-1 处原封不动留着 | 发现或修复模式化缺陷时，必须执行**同型扫（Sibling Sweep）**：用缺陷形状特征检索全仓，一并列出或修复同型位点 |
| 脚本链条里 `grep -c` 匹配为 0 时退出码为 1，导致 `&&` 或 `set -e` 提前静默中断 | 检查 Shell 脚本时，重点关注 `set -e` 下返回非零退出码的常规命令（如 `grep`、`diff`）是否缺少 `\|\| true` 保护 |
| 归一化重构把某个看似「异类」的特判改成了统一写法，结果重新引爆历史 Bug | 建议删除或合并看似不对称的特判前，先按 `review_plan.history_tracking` 的深度查 `git log -S` 或 `git blame`，确认该不对称是否是为了规避已知底层缺陷 |
| `--fix` 提交或修改时把 `__pycache__`、临时构建物或无关格式化带进工作区 | 修复前后必跑 `git status --short`，只触碰修单点名的目标文件与行段 |
| 将网络超时、沙箱限制、缺少可选依赖等环境报错当成代码缺陷报出 | 严格区分「环境与工具链故障」与「产品代码缺陷」；环境阻塞记入 `verification` 说明，不伪造成代码发现 |
